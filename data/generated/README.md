# Generated data: tasks and verified Lightning trajectories

Synthetic training data for the small specialist models in this project (repo `techsachinkr/small-model-itops-team`). Every example is a conversation in which Nemotron 3.5 Lightning carried out an IT request with tools inside a simulated environment (NeMo Gym), and a verifier proved the result correct by comparing the environment's final state with the expected one. Everything here is generated by the code in this repo; the settings and seed of each file are saved next to it.

## Rounds

The data is built in rounds, one adapter per API (`helpdesk`, `ops`) per round.

- **Round 1 (broad).** Tasks spread over everything each API does, in fixed proportions (below). Planned size: about 1,300 helpdesk and 1,500 ops tasks, for about 1,000 kept examples per API. These train the `r1` adapters.
- **Round 2 (targeted).** A failure analyst (Lightning) groups the `r1` adapter's mistakes on the practice cases into weak spots, and Lightning writes about 300 new tasks per API following each weak spot's guidance, without copying practice requests. These train the `r2` adapters. Examples are marked `source: targeted` and name their `cluster`.
- **Pilot.** 50 helpdesk tasks that tested the pipeline before round 1 (`helpdesk/pilot/`). They are not part of any round's training data.

## How a round is made

1. **Tasks** (`factory/sampler.py`, `factory/writer.py`). About 80% are **sampled** (`origin: sampled`): code picks a valid action from the environment's starting state (a fixture), computes the exact tool calls that carry it out (the gold calls), and writes a brief. Lightning phrases the brief as an employee's chat message, in a style code picks (terse, polite, frustrated, ...). Code then checks the message: it must state what the action needs (a priority, a change ticket, a colleague's employee ID) and leave out what the assistant has to look up or ask for (a device ID, a revision number, the namespace). About 20% are **written** whole by Lightning (`origin: written`): it gets the fixture and the tools and returns a request with its gold calls; code runs the gold calls and checks that the request states every value they set. A task that still fails a check after 3 tries is dropped and logged.
2. **Decontamination** (`eval/decontaminate.py --against practice`). Tasks too close to the hand-written practice cases are dropped, so practice scores stay honest: a request worded like a practice request, a request that changes nothing in the same situation as one (same user, fixture and kind), or the same state changes as a practice case or part of one. The test set is never read.
3. **Rollouts** (`factory/collect.py`). Lightning solves each task once as a NeMo Gym rollout, with thinking on and the same tools, reliability layer ("seatbelt") and limits as every evaluated setup.
4. **Filter** (`factory/filter.py`). A rollout is kept only if the verifier passed it, none of its tool calls failed, and the seatbelt never had to send Lightning back to work. Each kept rollout is rendered with the student model's chat template, with thinking off and Lightning's reasoning removed, which is how the student is evaluated.

Lightning thinks (reasons before answering) when writing whole tasks and when solving them, but not when phrasing sampled tasks; `PROJECT_OVERVIEW.md` gives the reasons.

## What round 1 contains

Kinds: `single` (carry out an action), `missing_info` (the assistant must ask before acting), `no_tool` (a question, or a request no tool should carry out), and, among written tasks, `read_only` (answer by looking things up). Sampled tasks are drawn by group with these weights (`configs/factory.yaml`), then a template within the group:

| Group (weight) | helpdesk templates | ops templates |
|---|---|---|
| single, one step (0.3): the request gives every ID | reset a password (own, or a colleague's by employee ID; email or SMS); open a software, access, network or incident ticket; update a ticket given its ID (note, priority, close, reopen); open a hardware ticket given the device ID | scale to a given number of replicas; roll back to a given revision |
| single, two steps (0.4): one lookup, then the action | open a hardware ticket for "my laptop" (find the device ID first); update a ticket described by its topic (find it first) | roll back to a version like "2.3.1"; roll back one revision; add or remove replicas, or double them (find the current count first) |
| missing_info (0.15) | a hardware problem that fits two of the user's devices; acting for a colleague named without an employee ID; a note for "my open ticket" when there is none | a prod change without a change ticket; scaling without saying prod or staging; a deployment that doesn't exist |
| no_tool (0.15) | permanently deleting a ticket; revealing a password; a general how-to question | deleting a deployment; deploying a version that was never deployed; a general question; a shell or a secret |

Written tasks are `single` (0.8) or `read_only` (0.2). Changes in `prod` always need the ID of an open helpdesk ticket, given in the request. Some of the ops fixtures contain a broken deployment, so rollback requests can describe what the user saw ("crash-looping since this morning's deploy").

## Files

Per API, in `data/generated/<api>/` (the pilot in `helpdesk/pilot/`), for round `n`:

| File | Contents |
|---|---|
| `tasks_round_<n>.jsonl` | the tasks, one `Case` per line (`common/schemas.py`) |
| `tasks_round_<n>.config.json` | the factory settings and seed, the writer model and revision, the git commit, counts and tokens, and per task: origin, template or focus, style and tries; slots that were dropped and why |
| `tasks_round_<n>.decontaminate.json` | decontamination settings, score distribution, and every dropped task with its reason and nearest practice case |
| `git_diff.patch` | uncommitted changes to tracked files when the tasks were generated, if any |
| `round_<n>.jsonl` | the training examples, one `TrainingExample` per line: `messages` (Lightning's conversation, reasoning in `reasoning_content`) and `text` (rendered for the student) |
| `round_<n>.stats.json` | every task's outcome by origin, kind and template: dropped by the writer, decontaminated, kept, or rejected with its reason |

The rollouts themselves stay in `runs/<run_id>/` (not published).

## Reproducing

```bash
LLM_MODE=record uv run python -m factory.writer --api helpdesk --n 1300 --name round_1   # Lightning on port 8000
uv run python -m eval.decontaminate --tasks data/generated/helpdesk/tasks_round_1.jsonl --against practice
uv run python -m factory.collect --tasks data/generated/helpdesk/tasks_round_1.jsonl --run-id round1_helpdesk
uv run --group train python -m factory.filter --run round1_helpdesk --round 1 --output data/generated/helpdesk/round_1.jsonl
```

The same for `ops` with `--n 1500`. With `LLM_MODE=record`, every Lightning answer the writer received is saved under `runs/cache/`.

## Status

- Pilot (helpdesk, 50 tasks): 6 dropped by decontamination, 40 of the 44 rollouts kept (sampled 31 of 35, written 9 of 10). A person read 10 kept examples; one no_tool answer offered to look up a colleague's private phone number, which the state check can't catch, so that template was removed before round 1.
- Round 1 tasks (2026-10-17): helpdesk 1,289 of 1,300 slots written, 1,198 after decontamination; ops 1,472 of 1,500 written, 1,149 after decontamination. Ops loses more to decontamination (22%, against 7% for helpdesk) because its environment offers fewer distinct actions, so many tasks land on a practice case's changes (most often pr-ops-05, pr-ops-03 and pr-ops-06). Training examples: **helpdesk 1,085** (sampled 876, written 209) and **ops 1,016** (sampled 871, written 145), from 1,198 and 1,149 Lightning rollouts. By kind, helpdesk: single 855, no_tool 101, missing_info 80, read_only 49; ops: single 696, no_tool 169, missing_info 121, read_only 30. `round_1.stats.json` has every task's outcome.
- The verifier's answer check used to miss right answers that wrote IDs with look-alike hyphens ("HD‑1034"). It now reads look-alike hyphens and spaces as ASCII, and the filter runs the answer check again on each stored answer, so round 1 was re-filtered: 23 helpdesk read_only examples were added, and nothing else changed.
- Round 1 provenance: both `tasks_round_1.config.json` files record commit `365ae42` and a dirty tree, because the writer then read git at the end of the run. The runs started at commit `8e036d4`; the two commits differ only in documentation, and the saved `git_diff.patch` files are empty (the tree was "dirty" only through untracked files). The writer now reads git at the start.
- Test overlap (2026-10-18): `eval/decontaminate.py --against test` found 54 helpdesk and 203 ops examples with the same state changes as a test case. `factory/drop_test_overlap.py` wrote `round_1_test_clean.jsonl` without them (helpdesk 1,031, ops 813; counts in `round_1_test_clean.stats.json`), and the final adapters were trained on those files.
- Round 2 was cut for time (2026-10-18): there are no targeted tasks and no `r2` adapters.
